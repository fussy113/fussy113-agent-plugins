# /github:review-dep-pr — 依存関係更新PRのレビュー

依存関係更新PR(Dependabot・Renovate・手動でのバージョン上げのいずれも)を、依存関係更新の観点から包括的にレビューします。

## 完了条件

次が出力に揃っていればレビュー完了とする。

- マージ可否の判定(🟢/🟡/🔴)とその理由
- 更新内容(パッケージ名・旧→新バージョン・semver種別)
- 依存関係の使用箇所を `path:line` で列挙した証跡
- Breaking changes に該当する箇所(無ければ「影響なし」)

このスキルはレビューのみを行う。コードの修正やPRへのコメント投稿はしない(必要なら `/github:fix-pr` に渡す)。

## 出力の指針

- **結論から書く**。判定セクション(`## 📊 判定`)を先頭に置き、マージ可否とその理由を先に示す。詳細は後ろに回す。
- **該当しないセクションは省略する**。「なし」「N/A」の羅列でテンプレートを埋めない。
- **気づいた点は軽微なものも省かず列挙する**。重要度の切り分けは判定セクションで行う(報告と絞り込みを分ける)。

## 実行手順

1. **PR情報の取得**
   - `gh pr view $ARGUMENTS` で基本情報、`gh pr diff $ARGUMENTS` で差分を取得する。
   - PR の作成元(Dependabot / Renovate / 手動)を確認する。以降で参照する付随情報が変わる(Dependabot はコミットメッセージ、Renovate は PR 本文にリンクされたリリースノート)。

2. **依存関係の更新内容を分析**

   - **更新内容**: パッケージ名、旧→新バージョン、semver 種別(メジャー=Breaking changes の可能性が高い / マイナー=新機能・後方互換 / パッチ=バグ修正・後方互換)。
   - **リリースノート**: `gh release view` や WebSearch / WebFetch でリリースページ・CHANGELOG を参照し、主な変更を要約する。
   - **Breaking changes**: メジャー更新の場合、非推奨 API の削除・変更、マイグレーションガイドの有無を調べる。
   - **セキュリティ**: セキュリティアップデートか、CVE番号・深刻度(Critical/High/Medium/Low)・影響範囲を確認する。
   - **互換性**: ランタイム要件(Node.js/Python/Ruby等)や peer dependencies との整合性を評価する。
   - **テスト結果**: `gh pr checks $ARGUMENTS` で CI ステータスを確認し、失敗があれば原因を調べる。

3. **プロジェクトコードへの影響調査**

   更新対象パッケージがコード内でどう使われているかを Grep(import/require 文の検索)で調べ、次を証跡として残す。

   - 使用箇所を `path:line` で列挙(合計ファイル数も示す)
   - Breaking changes に該当する箇所(該当する API・メソッドの使用有無)
   - 影響度(直接的な影響の大きさ / 変更の複雑さ)

4. **レビュー結果の出力**

   下記フォーマットで出力する(該当しないセクションは省略する)。

   ```markdown
   # 依存関係更新PR #{PR番号} レビュー結果

   ## 📊 判定

   **マージ推奨度**: [⭐⭐⭐⭐⭐ (5段階)]
   **結論**: [1〜2行。何をどう判断したか]
   **必要なアクション**: 次のいずれか1つを選び、該当項目を箇条書きする
   - 🟢 即座にマージ可能(パッチ更新でテスト通過 / Breaking changes なしのセキュリティ修正 / 互換性問題のないマイナー更新)
   - 🟡 以下の確認後にマージ — [確認すべき事項]
   - 🔴 マージ前に対応が必要 — [必要な対応]

   ## 📦 更新内容
   - `[package name]`: [current version] → [new version]([Major/Minor/Patch])

   ## 📋 リリースノート要約
   [主な変更点を箇条書き]

   ## 🔒 セキュリティ情報
   [セキュリティ更新の場合のみ。CVE番号 / 深刻度 / 脆弱性の詳細]

   ## ⚠️ Breaking Changes
   [ある場合のみ。詳細とマイグレーションパス]

   ## 🔍 互換性チェック
   - ランタイム要件: [問題なし / 要確認 — 内容]
   - 他の依存関係との整合性: [問題なし / 要確認 — 内容]

   ## ✅ テスト結果
   - CIステータス: [Pass/Fail/Pending]
   - [失敗しているテストがあれば原因]

   ## 🔎 プロジェクトコードへの影響

   ### 使用箇所(合計 [N] ファイル)
   - `path/to/file1.ts:15` — [使用方法]
   - `path/to/file2.js:42` — [使用方法]

   ### Breaking Changes の影響
   [影響を受ける箇所を `path:line` で列挙。無ければ「影響なし」の1行]

   ### 必要な対応
   [ファイルごとに必要な変更内容。無ければ「なし」の1行]

   ### 影響度
   - 直接的な影響: [高/中/低] ／ 変更の複雑さ: [高/中/低]

   ## 💡 その他の推奨事項
   [あれば]
   ```

## 効率の目安

パッチ / マイナー更新のレビューは低い effort でも精度が落ちにくい。まず軽く1パス通し、Breaking changes や使用箇所が多いと分かった時点で深掘りに切り替えるのが安い。判断に迷う場合は `/token-ops:effort-router` を参照。

## 注意事項

- 更新元に付随する情報(Dependabot のコミットメッセージ、Renovate の PR 本文にリンクされたリリースノート等)も確認する。
- セキュリティアップデートは優先的にマージを検討する。
- 複数の依存関係が同時に更新される場合は、それぞれについて評価する。
- 使用箇所が多い場合や影響が大きい場合は、段階的な移行計画を提案する。

## 使用例

```bash
/github:review-dep-pr 42
```

## 関連

- `/github:fix-pr` — レビュー後にコードの修正やコメント返信が必要な場合。
- `/dep-manager:migrate-dependabot` — Dependabot から Renovate へ移行したい場合(設定の投入・チューニングを担う。本スキルはレビュー専任でレイヤーが異なる)。
- `/token-ops:effort-router` — レビューの深さに応じた effort 見積もり。
